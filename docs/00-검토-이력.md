## 2. 질문 자체의 재정의

### "Agent가 우리 DB에 어떻게 접근하는가"는 Dooray에 물을 질문이 아니었음

Extension Agent는 **우리가 작성해서 우리 서버에서 실행하는 애플리케이션**.
DB 접근은 평소처럼 드라이버·사내 API로 직접 하면 되고, Dooray는 우리 DB의 존재를 알지도 못함.

이후 확보한 Dooray 연계 구성도가 이를 그대로 확인해줌:
- 점선 경계를 넘는 트래픽은 **Dooray ↔ Agent 간 요청/응답뿐**
- DB 조회도, LLM 호출도 모두 고객사 영역 내부에서 완결
- 가이드 원문: *"이 인터페이스는 새로운 권한 체계를 만들지 않습니다"*

### 실제로 물어야 했던 것

"Dooray와 우리 서버 사이의 경계가 어떻게 생겼는가" — 이게 정해져야
서버 위치, 방화벽 신청 여부, PoC 착수 방법이 결정됨.

**답**: Socket Mode(아웃바운드 WebSocket). 우리가 나가는 연결만 맺음.
→ 공인 IP·인바운드 오픈·인증서 전부 불필요. 개발 PC에서도 바로 가능.

## 4. 🔴 핵심 발견 — 가이드와 실제 SDK의 불일치

Dooray 위키 가이드는 SDK 리팩터링 **이전** 시점 문서. 그대로 따라 하면 동작하지 않음.

| 가이드 | 실제 (`0.1.0b1`) |
|---|---|
| zip/tar.gz 배포, `pip install -r requirements.txt` | PyPI 공개, `pip install --pre dooray-sdk` |
| `@agent.messenger` | deprecated (DeprecationWarning) |
| `event.reply(answer)` | deprecated |
| **`event.user_id`** | **존재하지 않는 속성** → `AttributeError` |
| "OpenAI, Azure OpenAI, Claude 등 지원" | **OpenAI / Azure OpenAI / Dooray AI 3종만 구현** |

→ 문서(개념)와 패키지(코드)를 분리해서 다루기로 결정. `01` / `02` 문서 분리의 이유.

## 5. 검토 중 발생한 오류와 정정

> 판단 근거를 남기기 위해 기록.

**1차 (오류)**: "`event.reply()`는 deprecated"
**2차 (잘못된 정정)**: 코드에서 `SocketModeRequest.reply()`가 경고를 발생시키지 않는 것을 보고
"정상 API"라고 정정 → **이 정정이 틀림**
**3차 (확정)**: README의 "Summary of deprecated surfaces" 표에 `req.reply(text)`가
명시적으로 deprecated로 등재되어 있음. **1차가 맞았음.**

**교훈**: SDK 소스의 경고 발생 여부와 공식 deprecation 정책이 일치하지 않을 수 있음.
`reply()`는 내부 설계상 "사용자 핸들러에서만 경고가 발생하도록" 처리되어 있어
코드만 보면 정상 API로 오인하기 쉬움. **README를 기준으로 삼을 것.**

## 6. 인프라 판단 — "새 PC에 설치해야 하나?"

**결론: 불필요.**

판단 기준은 "어떤 장비냐"가 아니라 **"조회 대상 DB·API에 닿느냐"** 하나뿐.
Socket Mode라 네트워크 요구사항이 거의 없기 때문.

| 단계 | 위치 | 근거 |
|---|---|---|
| 1 | 개발 PC | 페이로드 탐색 단계는 코드 수정 사이클이 짧아야 함 |
| 2 | Swarm (ai-node) | DB 경로 기확보. PC는 절전·재부팅으로 상시 연결 불가. `replicas: 2`로 HA 자동 |
| 3 | 보안·운영 고도화 | 마스킹·인젝션 방어·감사로그 |

**아웃바운드 실측 (사무망)**
```
https://infomax.dooray.com  → 302 (로그인 리다이렉트)
https://api.dooray.com      → 404 (루트에 페이지 없음)
```
둘 다 **TLS 핸드셰이크 성공** = 방화벽 통과. 차단이면 타임아웃/연결거부로 죽음.
→ 서버망(ai-node)에서 동일 확인 필요. 정책이 다를 수 있음.

## 7. 토큰이 블로커인 이유

단순 인증키가 아님. **토큰 = Dooray에 등록된 봇 그 자체.**

등록이 없으면 사내 메신저에 봇이 존재하지 않음 →
대화방에 초대할 대상도, 멘션할 상대도 없음 → 이벤트 유입 경로 자체가 없음.
코드가 완벽해도 아무 일도 일어나지 않는 상태.

**개발용/운영용 2개 발급이 필요한 이유**:
SDK가 토큰당 active WebSocket 1개만 허용(`1008 AGENT_ALREADY_CONNECTED`).
중복 접속은 STANDBY로 빠져 15초마다 재시도. PC와 서버에서 같은 토큰을 쓰면
한쪽이 **조용히** 비활성화되어 "왜 응답이 없지"로 시간을 낭비하게 됨.

## 8. 우선순위 판단

### 첫날의 목표는 에코가 아니라 페이로드 덤프

에코봇이 도는 순간, 문서로 확인되지 않던 항목들이 한 번에 풀림.
따라서 `req.to_dict()` 전체 덤프를 먼저 찍고 케이스별로 메시지를 던져보는 것이 우선.

확인 대상: 1:1 DM / 멘션 / **멘션 없는 일반 메시지** / 스레드 답글 / 파일 첨부

> 특히 "멘션 없는 메시지도 수신되는가"는 단순 기능 확인이 아님.
> 수신된다면 대화방 전체 내용이 우리 서버로 유입된다는 뜻이라 별도 개인정보 검토가 필요.

### 비즈니스 로직을 SDK와 분리해 선행 개발

실제 공수는 SDK 연결이 아니라 CRM 조회·포맷팅·마스킹에 있음.
분리해두면 토큰 없이도 `pytest`로 전부 검증 가능하고, 나중에 핸들러는 3줄로 연결됨.

여기서 미리 답이 나오는 것:
- CRM API 실제 응답 시간 (기획서 3초 권장 — 실측 필요)
- 마스킹 범위 (기획서 캡처에 담당자 이메일·휴대폰이 그대로 노출됨)
- 조회 권한 범위 (본인 담당 고객만 vs 전체)

## 9. 기획서 검토에서 나온 구조적 문제

### 검토서와 기획서가 서로 충돌

- Dooray 검토서: "버튼·드롭다운·카드 UI **미지원**"
- CRM 기획서: "**텍스트 카드 형태**의 결과값 응답"

→ 표현 가능 범위(마크다운 표 렌더링 여부 등)를 실측한 뒤 화면 설계를 확정해야 함.

### CRM 기획서의 3초 타임아웃

순수 조회는 가능하나 AI 분석이 들어가면 달성 불가.
SDK에 **메시지 수정 API가 없어서** "처리 중 → 결과 갱신" 우회도 바로는 안 됨
(REST API 직접 호출 필요).

### "현황판(Dooray! News)"의 실체

SDK가 제공하는 것은 **Task**와 **Wiki**. News는 별개 기능.
현황판을 **프로젝트/업무 보드**로 구현하면 `create_task` / `set_workflow` / `set_done`으로
현행 SDK에서 바로 가능. 기획서 캡처의 형태를 보면 업무 보드로 충분해 보임.

### 스레드 답장 미구현

`reply_in_thread` → `NotImplementedError`.
"원문 글타래에 회신"을 전제로 한 설계는 현재 불가. `reply_to_message`(인용 답장)로 대체 필요.

## 11. helpdesk 가이드 확보 후 변경된 판단 (2026-09-02 추가)

helpdesk "익스텐션 에이전트 이용가이드" + "Dooray! SDK 가이드" 확보로 두 가지가 뒤집힘.

### 토큰 블로커 해소 — 문의 불필요

토큰은 Dooray에 요청하는 것이 아니라 **AI 스튜디오에서 자체 발급**하는 것이었음.
리드타임 없음. 게다가 **1인당 5개** 생성 가능해서 개발/운영 토큰 분리 문제도 자동 해결.

→ 준비했던 "토큰 발급 절차 문의" 메일은 불필요해짐.

### 대신 라이선스가 새 블로커로 등장

익스텐션 에이전트는 **체험 기간 기능**이며 **AI 프리미엄 라이선스 보유자만** 사용 가능.
게다가 특정 테넌트 한정.

→ 문의 대상이 "토큰을 어떻게 받나"에서 **"우리가 대상에 포함되나"**로 바뀜.
→ 다만 이건 문의 전에 **AI 스튜디오 메뉴가 보이는지 직접 확인**하는 게 빠름.

### Task/Wiki API 판단 하향

패키지에는 Task 13종·Wiki 16종이 구현되어 있으나
**공식 SDK 가이드와 export 목록 어디에도 없음.** 공식 문서 범위는 메신저뿐.

→ 기존에 "현황판 기획은 Task API로 바로 가능"이라고 판단했으나,
**미문서화 API이므로 지원 보장이 없음**으로 하향. 기술미팅 안건 상위로 이동.

### 개인정보 이슈 구체화

이용가이드: *"에이전트가 초대된 대화방에 메시지 전송 시 해당 에이전트가 메시지를 조회하고
답변을 보낼 수 있음"* + *"누구나 자유롭게 대화방에 초대 가능"*

→ 멘션 없는 메시지도 유입될 가능성이 높고, 의도치 않은 대화방에 봇이 들어갈 수 있음.
→ 조기 반환·로깅 정책·채널 화이트리스트를 설계에 반영.

### 기타 정정

- `query()`는 `options.langchain_config` **필수** — 위키 가이드의 `query(prompt=...)` 단독 호출은 동작하지 않음
- `DoorayAIConfig` 존재 → 에이전트 토큰으로 Dooray AI를 LLM으로 사용 가능
- `WebClient.put()` 존재 → 메시지 수정 REST 우회 경로 확보
- function calling(`tools`) 지원 확인
- 메시지 ID 경로는 `req.entity.data.id`

# 2026-09-03 — 버튼, 알림, 그리고 접수

## 13. "버튼이 반드시 되어야 한다"

배부장님 요구는 명확했다. 업무 처리 상태를 대화방에서 **버튼으로** 바꿀 수
있어야 한다는 것.

### 순진했던 첫 시도

메신저 API로 보내는 메시지에 `attachments.actions`를 넣으면 될 줄 알았다.
**버튼은 그려졌다.** 그런데 눌러도 아무 일이 없었다.

애매해서 확실히 가렸다 — **진짜 업무를 바꾸는 값**을 실어 보내고 눌러봤다.

```
클릭 후 상태 : registered      ← 서버까지 오지 않았다
```

개인 토큰으로 보낸 메시지의 버튼이 **어느 앱 것인지 Dooray가 알 방법이 없다.**
`callbackId`를 앱과 연결할 고리가 없기 때문이다.

> **버튼이 실제로 동작하는 곳은 슬래시 커맨드 응답뿐이다.**

이걸 몰라서 처음엔 `#확인` 같은 텍스트 확인으로 만들었다가, 나중에 슬래시
커맨드 쪽으로 다시 설계했다.

### 두 번째 벽

그러면 양식 접수를 통째로 커맨드로 옮기면 되겠다고 생각했다. 그런데
**슬래시 커맨드에는 여러 줄을 실을 수 없다.**

`/커맨드` 뒤에 Shift+Enter로 개행하면 커맨드로 인식되지 않고 **일반 메시지로**
전송된다. 7줄짜리 요청서 양식을 인자로 넘길 방법이 없다.

### 우회 — 순서를 뒤집었다

정면으로는 길이 없어서 방향을 바꿨다.

```
양식은 일반 메시지로 올린다
  → /접수 커맨드가 GET /channels/{id}/logs 로
     방의 로그에서 그 사람의 마지막 양식을 찾아 읽는다
  → 커맨드 응답이므로 [생성][취소] 버튼이 동작한다
```

**판단**: `#확인` 경로도 남겼다. 버튼은 클릭이 하나 더 들지만 눌러서 끝나고,
텍스트는 한 줄 더 치지만 빠르다. 시연에는 버튼, 실무에는 텍스트가 편하다.
정원석님 판단으로 둘 다 유지.

## 14. Dooray! News — 절반만 가능했다

"완료되면 News로 알림이 오게 할 수 없나"라는 질문에서 출발했다.

### 방향을 잘못 보고 있었다

그때까지 우리가 확인한 건 **Dooray가 자동으로 보내주는 알림**이었고, 상태
변경에는 알림이 없다는 결론이었다. 그래서 "안 된다"고 답했었다.

그런데 News가 **무엇인지** 다시 보니 길이 있었다. News는 개인 봇 채널이고
**채널 ID가 그 사람의 memberId와 같다.** 완료 알림을 *파싱*할 때 쓰던 사실인데,
반대로 *쓰는* 데도 쓸 수 있었다.

```
POST /messenger/v1/channels/{내 memberId}/logs   →  200
```

**두레이가 안 보내줄 뿐, 우리가 넣는 건 막혀 있지 않았다.**

### 그런데 남의 News는 막혀 있었다

```
POST /messenger/v1/channels/{남의 memberId}/logs
  →  500  CHANNEL_NOT_JOINED_MEMBER_ERROR
```

**그 채널의 멤버가 아니어서다.** Dooray-Bot이 모두의 News에 쓰는 것은 시스템 봇
권한이라 개인 토큰으로는 흉내 낼 수 없다. **우회로가 아니라 권한의 벽이다.**

→ 대안으로 1:1 대화방을 시험했고 200이 나왔다. **본인이면 News, 남이면 1:1**로
갈라 보내는 것으로 확정.

### ⚠️ 정정 — 중복을 막느라 필요한 알림까지 껐다

버튼 완료와 폴링이 같은 사건에 각자 반응해 통보가 두 번 가는 문제를 고치면서,
`reply_for_task`를 통째로 막았다. **그런데 이 함수는 두 가지를 함께 결정한다** —
대화방 인용 답장과 요청자 개인 통보(News/1:1). 봇 공지와 겹치는 것은 앞의
하나뿐인데 뒤의 것까지 사라졌다.

정원석님이 "풀링으로 오는 게 두레이 뉴스로 오는 거냐"고 물어보지 않았다면
시연 때까지 몰랐을 것이다. **하루 종일 찾던 바로 그 알림이 조용히 죽어 있었다.**

→ 버튼 경로의 개인 통보를 커맨드 서버가 직접 보내도록 옮겼다. 폴링을 건너뛰게
만든 이상 그 일을 대신할 주체가 필요했고, 덕분에 5분을 기다리지 않고 즉시 간다.

**교훈**: 한 함수가 두 결정을 겸하고 있으면, 그중 하나만 끄려다 둘 다 끈다.

## 15. 작성자는 참조자가 될 수 없다

요청자를 참조자(cc)로 넣으면 Dooray 기본 알림이 갈 것이라 기대했다.
그런데 `users.cc`가 **빈 배열**로 돌아왔다. 오류도 없이 조용히 무시된다.

봇이 곧 작성자인 구조에서는 요청자를 참조자로 만들 수 없다는 뜻이다.

→ 요청자 ID를 **업무 본문에 직접 남기기**로 했다.

```
[요청출처] channel={채널ID} message={메시지ID} requester={요청자ID}
```

**판단**: `requester_id`가 참조자 지정까지 겸하던 것을 `cc_requester`로 분리하고
기본을 껐다. 참조는 등록 시점 알림만 만들고 상태 변경에는 효과가 없어, 접수
회신과 겹치는 중복 알림만 남기 때문이다.

## 16. 두 프로세스가 같은 사건에 반응한다

버튼으로 완료하면 커맨드 서버(ai-node)가 그 자리에서 봇 공지를 띄우는데,
완료 감지 폴링(맥)이 같은 변화를 5분 안에 또 잡아 인용 답장을 달았다.
**같은 사실이 두 번 알려졌다.**

두 프로세스는 다른 기계에서 돌아 상태를 나눌 매체가 없다. 검토한 선택지:

| 방법 | 판단 |
|---|---|
| 폴링을 없앤다 | ✗ 두레이 웹에서 직접 완료하는 경로를 놓친다 |
| 상태 저장소를 공유한다 | ✗ 기계가 달라 비용이 크다 |
| **업무 본문에 표식** | ✅ 워처가 어차피 본문을 읽으므로 읽는 쪽 비용이 0 |

```
[통보완료] button      ← 이 줄이 있으면 폴링이 건너뛴다
```

표식은 **통보를 보낸 뒤에** 남긴다. 순서가 반대면 통보 실패 시 폴링마저 건너뛰어
아무도 모르는 채로 끝난다.

### 곁들여 — 완료 공지가 멱등이 아니었다

지난 목록에 남아 있던 `[완료]`를 다시 누르면 공지가 또 나갔다(실측: 오후 1:57,
1:58 두 번). 공지를 배경 작업으로 옮겨 표식을 먼저 확인하도록 고쳤다.

## 17. 요청서 양식 — 자유 서술과 목적이 다르다

"요청 유형을 입력하면 양식을 주고, 채워서 내면 업무가 생기게" 라는 요구.

이미 자유 서술 접수가 있는데 왜 또 필요한가를 정리했다.

| | 자유 서술 (`service.py`) | 양식 (`form.py` · `intake.py`) |
|---|---|---|
| 전제 | 사람이 쓰던 대로 쓴다 | **빠뜨리기 쉬운 항목을 미리 묻는다** |
| 쓰는 상황 | 대화 중 자연스럽게 | **전화로 받아 적을 때** |
| AI 역할 | 문장을 읽고 유형·제목을 뽑는다 | 항목이 이미 갈려 있어 규칙만으로 충분 |

**둘 다 남기기로 했다.** 상황이 다르다.

### 설계에서 신경 쓴 것

- **제목은 CRM 고객사명으로.** 양식의 「고객명」에는 부서·담당자가 섞여 있어
  제목으로 쓰기엔 길다. 원문은 본문에 그대로 보존한다.
- **대기는 (대화방, 사람)별로.** 한 방에서 두 사람이 동시에 양식을 내도 서로의
  것을 확정해 버리지 않는다. 10분이 지나면 버린다.
- **양식 유형은 추출기 라벨과 글자까지 같아야 한다.** 어긋나면 같은 요청이 접수
  경로에 따라 제목에서 다른 이름으로 갈려 현황판에서 한 종류로 묶이지 않는다.
  그걸 지키는 테스트를 붙였다.

### ⚠️ 정정 — 확인 문구가 버튼처럼 보였다

`생성 #확인    취소 #취소` 라고 써 놓았더니 정원석님이 "이거 기능이 있나"고
물었다. **눌러 보게 만드는 모양이었다.** 문장으로 못박고, 버튼을 쓰려면
`/접수`라는 것도 함께 알리도록 고쳤다.

## 18. 인바운드 — 사내망이 막았다

버튼 클릭은 **Dooray가 우리 서버를 호출**한다. 공개 HTTPS URL이 필요했다.

### ngrok 좌절

터널 자체가 HTTP 403으로 막혔다. 인증서를 보니 원인이 분명했다.

```
issuer=CN=FG6H1FTB25900086, O=Fortinet
```

사내 Fortinet TLS 가로채기. **터널에 도달한 요청이 0건**이었다.

### ai-node로 전환

퇴사자가 만든 R1 서버는 접근이 어려웠고, 새 서버를 만들 필요도 없었다.
`ai-node`에 공인 IP·Traefik·Let's Encrypt·`*.infomaxai.com` 와일드카드 DNS가
**이미 다 있었다.** 새 서버도 DNS 작업도 필요 없었다.

### 배포에서 막힌 두 가지

**① Swarm이 이미지 없는 노드에 배치했다.** 로컬 빌드 이미지는 빌드한 노드에만
있는데 Swarm이 ai-node-2~5에 배치해 전부 `No such image`로 죽었다.
→ `node.hostname` 제약으로 고정.

**② Traefik v3.1에서 라벨명이 바뀌었다.**

```
traefik.docker.network   →   traefik.swarm.network
```

옛 이름을 쓰면 Traefik이 컨테이너 IP를 못 골라 라우터를 아예 등록하지 않고,
**기본 자체서명 인증서**를 내민다. `curl: (60) self-signed certificate`가 이것
때문이었다. 인증서 문제로 보이지만 실은 라벨 문제다.

## 19. 성능 — N+1을 걷어냈다

버튼 클릭 후 목록을 다시 그리려니 조회가 한 번 더 늘 것 같아 확인해 봤더니,
기존 코드가 **목록을 받은 뒤 건별로 또 조회**하고 있었다.

실측해 보니 `GET /posts` 응답 한 건에 `subject`·`number`·`workflowClass`가
**이미 다 들어 있었다.** 건별 조회를 할 이유가 없었다.

```
/command      0.61s   (목록 1회)
/interactive  1.16s   (워크플로 + 상태 변경 + 목록 갱신)
```

**교훈**: 기능을 더하기 전에 그 경로의 비용을 한 번 재보면, 원래 있던 낭비가
드러나는 일이 잦다.
