## 2. 질문 자체의 재정의

### "Agent가 우리 DB에 어떻게 접근하는가"는 Dooray에 물을 질문이 아니었음

Extension Agent는 **우리가 작성해서 우리 서버에서 실행하는 애플리케이션**.
DB 접근은 평소처럼 드라이버·사내 API로 직접 하면 되고, Dooray는 우리 DB의 존재를 알지도 못함.

이후 확보한 Dooray 연계 구성도가 이를 그대로 확인해줌:
- 점선 경계를 넘는 트래픽은 **Dooray ↔ Agent 간 요청/응답뿐**
- DB 조회도, LLM 호출도 모두 고객사 영역 내부에서 완결
- 가이드 원문: *"이 인터페이스는 새로운 권한 체계를 만들지 않습니다"*

### 실제로 물어야 했던 것

"Dooray와 우리 서버 사이의 경계가 어떻게 생겼는가" — 이게 정해져야
서버 위치, 방화벽 신청 여부, PoC 착수 방법이 결정됨.

**답**: Socket Mode(아웃바운드 WebSocket). 우리가 나가는 연결만 맺음.
→ 공인 IP·인바운드 오픈·인증서 전부 불필요. 개발 PC에서도 바로 가능.

## 4. 🔴 핵심 발견 — 가이드와 실제 SDK의 불일치

Dooray 위키 가이드는 SDK 리팩터링 **이전** 시점 문서. 그대로 따라 하면 동작하지 않음.

| 가이드 | 실제 (`0.1.0b1`) |
|---|---|
| zip/tar.gz 배포, `pip install -r requirements.txt` | PyPI 공개, `pip install --pre dooray-sdk` |
| `@agent.messenger` | deprecated (DeprecationWarning) |
| `event.reply(answer)` | deprecated |
| **`event.user_id`** | **존재하지 않는 속성** → `AttributeError` |
| "OpenAI, Azure OpenAI, Claude 등 지원" | **OpenAI / Azure OpenAI / Dooray AI 3종만 구현** |

→ 문서(개념)와 패키지(코드)를 분리해서 다루기로 결정. `01` / `02` 문서 분리의 이유.

## 5. 검토 중 발생한 오류와 정정

> 판단 근거를 남기기 위해 기록.

**1차 (오류)**: "`event.reply()`는 deprecated"
**2차 (잘못된 정정)**: 코드에서 `SocketModeRequest.reply()`가 경고를 발생시키지 않는 것을 보고
"정상 API"라고 정정 → **이 정정이 틀림**
**3차 (확정)**: README의 "Summary of deprecated surfaces" 표에 `req.reply(text)`가
명시적으로 deprecated로 등재되어 있음. **1차가 맞았음.**

**교훈**: SDK 소스의 경고 발생 여부와 공식 deprecation 정책이 일치하지 않을 수 있음.
`reply()`는 내부 설계상 "사용자 핸들러에서만 경고가 발생하도록" 처리되어 있어
코드만 보면 정상 API로 오인하기 쉬움. **README를 기준으로 삼을 것.**

## 6. 인프라 판단 — "새 PC에 설치해야 하나?"

**결론: 불필요.**

판단 기준은 "어떤 장비냐"가 아니라 **"조회 대상 DB·API에 닿느냐"** 하나뿐.
Socket Mode라 네트워크 요구사항이 거의 없기 때문.

| 단계 | 위치 | 근거 |
|---|---|---|
| 1 | 개발 PC | 페이로드 탐색 단계는 코드 수정 사이클이 짧아야 함 |
| 2 | Swarm (ai-node) | DB 경로 기확보. PC는 절전·재부팅으로 상시 연결 불가. `replicas: 2`로 HA 자동 |
| 3 | 보안·운영 고도화 | 마스킹·인젝션 방어·감사로그 |

**아웃바운드 실측 (사무망)**
```
https://infomax.dooray.com  → 302 (로그인 리다이렉트)
https://api.dooray.com      → 404 (루트에 페이지 없음)
```
둘 다 **TLS 핸드셰이크 성공** = 방화벽 통과. 차단이면 타임아웃/연결거부로 죽음.
→ 서버망(ai-node)에서 동일 확인 필요. 정책이 다를 수 있음.

## 7. 토큰이 블로커인 이유

단순 인증키가 아님. **토큰 = Dooray에 등록된 봇 그 자체.**

등록이 없으면 사내 메신저에 봇이 존재하지 않음 →
대화방에 초대할 대상도, 멘션할 상대도 없음 → 이벤트 유입 경로 자체가 없음.
코드가 완벽해도 아무 일도 일어나지 않는 상태.

**개발용/운영용 2개 발급이 필요한 이유**:
SDK가 토큰당 active WebSocket 1개만 허용(`1008 AGENT_ALREADY_CONNECTED`).
중복 접속은 STANDBY로 빠져 15초마다 재시도. PC와 서버에서 같은 토큰을 쓰면
한쪽이 **조용히** 비활성화되어 "왜 응답이 없지"로 시간을 낭비하게 됨.

## 8. 우선순위 판단

### 첫날의 목표는 에코가 아니라 페이로드 덤프

에코봇이 도는 순간, 문서로 확인되지 않던 항목들이 한 번에 풀림.
따라서 `req.to_dict()` 전체 덤프를 먼저 찍고 케이스별로 메시지를 던져보는 것이 우선.

확인 대상: 1:1 DM / 멘션 / **멘션 없는 일반 메시지** / 스레드 답글 / 파일 첨부

> 특히 "멘션 없는 메시지도 수신되는가"는 단순 기능 확인이 아님.
> 수신된다면 대화방 전체 내용이 우리 서버로 유입된다는 뜻이라 별도 개인정보 검토가 필요.

### 비즈니스 로직을 SDK와 분리해 선행 개발

실제 공수는 SDK 연결이 아니라 CRM 조회·포맷팅·마스킹에 있음.
분리해두면 토큰 없이도 `pytest`로 전부 검증 가능하고, 나중에 핸들러는 3줄로 연결됨.

여기서 미리 답이 나오는 것:
- CRM API 실제 응답 시간 (기획서 3초 권장 — 실측 필요)
- 마스킹 범위 (기획서 캡처에 담당자 이메일·휴대폰이 그대로 노출됨)
- 조회 권한 범위 (본인 담당 고객만 vs 전체)

## 9. 기획서 검토에서 나온 구조적 문제

### 검토서와 기획서가 서로 충돌

- Dooray 검토서: "버튼·드롭다운·카드 UI **미지원**"
- CRM 기획서: "**텍스트 카드 형태**의 결과값 응답"

→ 표현 가능 범위(마크다운 표 렌더링 여부 등)를 실측한 뒤 화면 설계를 확정해야 함.

### CRM 기획서의 3초 타임아웃

순수 조회는 가능하나 AI 분석이 들어가면 달성 불가.
SDK에 **메시지 수정 API가 없어서** "처리 중 → 결과 갱신" 우회도 바로는 안 됨
(REST API 직접 호출 필요).

### "현황판(Dooray! News)"의 실체

SDK가 제공하는 것은 **Task**와 **Wiki**. News는 별개 기능.
현황판을 **프로젝트/업무 보드**로 구현하면 `create_task` / `set_workflow` / `set_done`으로
현행 SDK에서 바로 가능. 기획서 캡처의 형태를 보면 업무 보드로 충분해 보임.

### 스레드 답장 미구현

`reply_in_thread` → `NotImplementedError`.
"원문 글타래에 회신"을 전제로 한 설계는 현재 불가. `reply_to_message`(인용 답장)로 대체 필요.

## 10. 커뮤니케이션 판단

전상수 팀장님도 Dooray에서 전달받은 내용을 옮기는 입장일 가능성이 높음.
→ 긴 기술 질문 목록을 한 번에 던지면 "확인해보겠다"로 며칠 지연됨.

**전략**: 자료(특히 샘플 코드)부터 짧게 요청 → 직접 돌려보고 → 남는 것만 기술미팅 안건으로 정리.

실제로 이 방식이 유효했음. 문서 하나에서 PyPI 링크를 발견해 SDK를 직접 확보했고,
그 결과 애초 준비했던 기술 질문 목록의 상당수가 자체 해결됨.

**현재 남은 문의는 토큰 발급 하나뿐.**

## 11. helpdesk 가이드 확보 후 변경된 판단 (2026-09-02 추가)

helpdesk "익스텐션 에이전트 이용가이드" + "Dooray! SDK 가이드" 확보로 두 가지가 뒤집힘.

### 토큰 블로커 해소 — 문의 불필요

토큰은 Dooray에 요청하는 것이 아니라 **AI 스튜디오에서 자체 발급**하는 것이었음.
리드타임 없음. 게다가 **1인당 5개** 생성 가능해서 개발/운영 토큰 분리 문제도 자동 해결.

→ 준비했던 "토큰 발급 절차 문의" 메일은 불필요해짐.

### 대신 라이선스가 새 블로커로 등장

익스텐션 에이전트는 **체험 기간 기능**이며 **AI 프리미엄 라이선스 보유자만** 사용 가능.
게다가 특정 테넌트 한정.

→ 문의 대상이 "토큰을 어떻게 받나"에서 **"우리가 대상에 포함되나"**로 바뀜.
→ 다만 이건 문의 전에 **AI 스튜디오 메뉴가 보이는지 직접 확인**하는 게 빠름.

### Task/Wiki API 판단 하향

패키지에는 Task 13종·Wiki 16종이 구현되어 있으나
**공식 SDK 가이드와 export 목록 어디에도 없음.** 공식 문서 범위는 메신저뿐.

→ 기존에 "현황판 기획은 Task API로 바로 가능"이라고 판단했으나,
**미문서화 API이므로 지원 보장이 없음**으로 하향. 기술미팅 안건 상위로 이동.

### 개인정보 이슈 구체화

이용가이드: *"에이전트가 초대된 대화방에 메시지 전송 시 해당 에이전트가 메시지를 조회하고
답변을 보낼 수 있음"* + *"누구나 자유롭게 대화방에 초대 가능"*

→ 멘션 없는 메시지도 유입될 가능성이 높고, 의도치 않은 대화방에 봇이 들어갈 수 있음.
→ 조기 반환·로깅 정책·채널 화이트리스트를 설계에 반영.

### 기타 정정

- `query()`는 `options.langchain_config` **필수** — 위키 가이드의 `query(prompt=...)` 단독 호출은 동작하지 않음
- `DoorayAIConfig` 존재 → 에이전트 토큰으로 Dooray AI를 LLM으로 사용 가능
- `WebClient.put()` 존재 → 메시지 수정 REST 우회 경로 확보
- function calling(`tools`) 지원 확인
- 메시지 ID 경로는 `req.entity.data.id`
