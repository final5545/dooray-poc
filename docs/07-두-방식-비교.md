## 0. 근거의 성격 — 먼저 읽을 것

이 문서의 비교는 **양쪽의 근거 수준이 다르다.**

| 표기 | 의미 |
|---|---|
| ✅ **실측** | 실제로 돌려보고 확인함 |
| 📄 **문서** | Dooray 공식 문서·가이드에 적힌 내용 |
| 🔍 **소스** | SDK 패키지 소스를 읽어 확인 |
| ❓ **추정** | 근거가 있으나 직접 확인하지 못함 |

**우리는 정식 익스텐션 에이전트를 한 번도 써본 적이 없다.**
AI 프리미엄 라이선스가 없어 생성 자체가 불가능했다.
따라서 정식 방식에 대한 서술은 대부분 📄문서와 🔍소스이고,
자체 구현에 대한 서술은 대부분 ✅실측이다.

이 비대칭을 감안해서 읽어야 한다. 정식 방식의 실제 동작이 문서와 다를 가능성은
이미 여러 번 확인됐다 — 위키 가이드의 샘플 코드는 동작하지 않고,
공식 문서의 "파일 첨부 수신 불가" 서술은 실측에서 뒤집혔다.

## 1. 요약

Dooray가 정의한 익스텐션 에이전트의 주요 역할은 다음 넷이다.

1. Dooray! SDK(Python)를 통한 요청 수신
2. 내/외부 DB(API, Search, RAG) 조회
3. 필요 시 외부 LLM 호출 및 응답 생성
4. 보안 가이드라인을 준수하는 안전한 데이터 처리(프록시 역할)

**우리 구현은 이 넷을 모두 수행한다.** 다만 1번의 수단이 다르다 —
SDK를 런타임으로 쓰지 않고, SDK 소스에서 알아낸 프로토콜로 직접 붙었다.

2·3·4번은 애초에 고객사 영역이라 **방식과 무관하게 동일**하다.
DB 조회도, LLM 호출도, 마스킹·가드레일도 우리가 짜고 우리 서버에서 돈다.
Dooray는 이 셋에 관여하지 않는다.

### 한 줄 판정

| | |
|---|---|
| **기능** | 대등하거나 자체 구현이 넓다 (수신 이벤트 기준) |
| **정체성·권한** | 정식이 명백히 낫다 |
| **운영 통제** | 정식이 낫다 (킬 스위치·감사) |
| **진입 비용** | 자체 구현이 낫다 (라이선스 불요) |
| **지속 가능성** | 정식이 낫다 (공식 지원) |

→ **PoC는 자체 구현으로 충분하고, 운영은 정식 전환을 목표로 두는 것이 맞다.**
   다만 전환의 실익은 "기능"이 아니라 **"정체성·권한 분리"**에 있다(§4).

## 2. 두 방식의 정의

### 2.1 정식 익스텐션 에이전트

```
AI 스튜디오에서 에이전트 생성
  → 에이전트 토큰 발급
  → dooray-sdk 로 Socket Mode 연결
  → 대화방에 봇을 초대해서 사용
```

- 봇이 **별도의 조직 구성원**으로 존재한다 📄
- 토큰은 그 봇의 자격증명이다 📄
- AI 프리미엄 라이선스 보유자만 생성 가능, 1인 5개 📄

### 2.2 자체 구현 (현행)

```
설정 > API > 개인 액세스 토큰 발급
  → 동일한 socket-mode 엔드포인트를 직접 호출
  → 사용자 본인 계정의 메신저 소켓에 연결
  → 화이트리스트로 처리 대상 채널을 제한
```

- **봇이 곧 사용자 본인**이다 ✅
- SDK 소스 분석에서 인증이 에이전트 전용이 아님을 확인했다 🔍
  (`Authorization: dooray-api`, `/common/v1/...`, `organizationMemberId`,
   `/messenger/v5/ws/{tenant}/{member}` — `02` §2)
- 라이선스 불요, 즉시 착수 가능 ✅

## 3. Dooray가 정의한 역할별 대조

### 역할 1 — 요청 수신

| | 정식 | 자체 구현 |
|---|---|---|
| 연결 방식 | Socket Mode (아웃바운드 WSS) 📄 | **동일한 엔드포인트** ✅ |
| 인증 | 에이전트 토큰 📄 | 개인 액세스 토큰 ✅ |
| 수신 필터 | SDK가 `channelLog` + `create`/`update`만 통과 🔍 | **원본 프레임 전부** ✅ |
| 수신 못 하는 것 | `delete`, `reaction`, 봇알림(`type=2`) 🔍 | 없음 ✅ |
| 재연결 | SDK 내장. 끊긴 뒤 토큰 재발급 🔍 | 만료 **전** 선제 갱신 ✅ |
| TLS | SDK가 `sslopt` 미전달 → macOS에서 연결 실패 🔍 | `certifi` 사용 ✅ |

**이 항목은 자체 구현이 넓다.** SDK가 버리는 이벤트가 실제로 필요했다 —
완료 알림(`type=2`)이 대표적이고, 이걸 못 받으면 오늘 만든 통보 기능이 성립하지 않는다.

> 단, 정식 방식에서도 SDK를 쓰지 않고 에이전트 토큰으로 직접 붙는 것은 가능하다.
> 즉 이 차이는 "정식 vs 자체"의 차이라기보다 **"SDK 사용 vs 직접 구현"**의 차이다.

### 역할 2 — 내/외부 DB 조회

**차이 없음.** 양쪽 모두 고객사 영역에서 우리가 직접 붙는다.
Dooray는 우리 DB의 존재를 모르고, 경계를 넘는 트래픽은 Dooray ↔ 에이전트 요청/응답뿐이다(`01` §2).

현재 구현: `crm/client.py`가 HTTP 어댑터, 필드 매핑을 설정으로 분리.

### 역할 3 — 외부 LLM 호출

| | 정식 | 자체 구현 |
|---|---|---|
| SDK `query()` 지원 프로바이더 | OpenAI / Azure OpenAI / Dooray AI 3종뿐 🔍 | 제약 없음 ✅ |
| Claude·Gemini | SDK에 config 클래스 없음 🔍 | 공식 SDK로 직접 호출 ✅ |
| `DoorayAIConfig` | 에이전트 토큰으로 Dooray AI 사용 가능 🔍 | **불가** — 에이전트 토큰이 없다 |
| 비용 부담 | 고객사 📄 | 고객사 ✅ |

**한 가지는 정식이 낫다** — `DoorayAIConfig`로 에이전트 토큰을 그대로 써서
Dooray AI를 LLM으로 쓸 수 있다. 별도 LLM 계약 없이 PoC가 가능했을 것이다.

현재는 Claude Haiku 4.5를 직접 호출한다(건당 약 1원, 지연 1.1초).

### 역할 4 — 보안 가이드라인 준수 (프록시)

**차이 없음 — 둘 다 고객사 책임이다.**

Dooray 가이드가 명시하듯, Extension Agent 경로는 **Dooray AI 게이트웨이를 거치지 않으므로**
지란지교 DLP·프롬프트 인젝션 탐지 등의 가드레일이 적용되지 않는다(`01` §4).
마스킹·인젝션 방어·감사로그는 방식과 무관하게 우리가 구성해야 한다.

> 다만 **§4의 권한 문제 때문에 자체 구현이 보안상 불리하다.**
> 프록시로서의 코드는 같아도, 그 프록시가 쥔 자격증명의 범위가 다르다.

## 4. 🔴 정식이 명백히 나은 것 — 정체성과 권한

여기가 두 방식의 **본질적 차이**다. 기능이 아니라 신원의 문제다.

### 4.1 토큰 권한 범위

| | 정식 | 자체 구현 |
|---|---|---|
| 토큰이 대표하는 주체 | 봇 📄 | **사용자 본인** ✅ |
| 접근 가능 범위 | 봇에게 허용된 서비스 📄 | **본인 계정 전체** — 메일·드라이브·프로젝트·캘린더 ✅ |
| 격리 | 가능 | **불가능** |

개인 액세스 토큰 화면에도 *"토큰을 사용하면 사용자 본인과 같은 권한으로 API를
사용할 수 있으므로 안전하게 보관해 주세요"*라고 적혀 있다 ✅.

**봇 프로세스가 탈취되면 담당자 계정 전체가 노출된다.** 정식 방식에는 없는 위험이다.

### 4.2 발신자·작성자 표시

| | 정식 | 자체 구현 |
|---|---|---|
| 메시지 발신자 | 봇 이름 📄 | **정원석** ✅ |
| 업무 작성자 | 봇 📄 | **정원석** ✅ |
| 조직도 표시 | 에이전트 설명 문구 표시 📄 | 해당 없음 |

시연·운영에서 "봇이 답한 것"이 아니라 "담당자가 답한 것"으로 보인다.
사용자 혼란뿐 아니라, 나중에 책임 소재를 가릴 때도 문제가 된다.

### 4.3 🔴 작성자 제약 — 실제로 기능을 막았다

**Dooray는 업무 작성자에게 그 업무의 알림을 보내지 않는다** ✅실측.
UI에서도 작성자는 참조자로 추가할 수 없다 ✅.

자체 구현에서는 봇 = 본인 = 작성자이므로:

```
봇이 티켓 생성 → 봇이 작성자 → 봇은 그 티켓의 알림을 영원히 못 받음
```

완료 감지를 푸시로 하려던 시도가 전부 여기서 막혔다.
웹훅·자동화·Dooray! News·참조자 지정을 모두 확인했으나
작성자 제약을 우회할 방법이 봇 계정 하나로는 없었다(`06` §6).

→ **폴링으로 우회했다.** 동작에는 문제가 없으나,
   정식 방식(또는 봇 전용 계정)이었다면 필요 없었을 구현이다 ❓.

> ❓ 표기 이유: 정식 에이전트에서 상태 변경 알림이 오는지는 확인하지 못했다.
> 작성자 제약은 풀리겠지만, **"상태 변경에는 아예 알림이 없다"**는 규칙이
> 플랫폼 전역이라면 정식 방식에서도 폴링이 필요하다. 기술미팅 안건.

### 4.4 긴급 정지

| | 정식 | 자체 구현 |
|---|---|---|
| 정지 방법 | AI 스튜디오에서 '사용 안 함' 전환 📄 | 토큰 삭제 ✅ |
| 코드 배포 필요 | 불요 📄 | 불요 |
| 부수 피해 | 없음 | **본인 계정의 다른 API 사용도 같이 중단** |

정식은 대화방에 `에이전트명(비활성화)`으로 표시되어 사용자도 상태를 안다 📄.

### 4.5 감사 추적

정식은 봇 활동이 봇 계정으로 남는다 📄.
자체 구현은 **사람의 활동과 봇의 활동이 같은 계정에 섞인다** ✅.
사후 조사 시 "이 메시지를 사람이 보냈나 봇이 보냈나"를 구분해야 하는데,
WebSocket 프레임의 `token` 필드로는 구분되지만 **REST 조회로는 구분되지 않는다** ✅(`06` §7).

## 5. 자체 구현이 나은 것

솔직하게 정리하면 다음 다섯이다.

### 5.1 진입 비용

| | 정식 | 자체 구현 |
|---|---|---|
| 라이선스 | AI 프리미엄 필요 📄 | 불요 ✅ |
| 테넌트 조건 | 특정 테넌트 한정(체험 기간) 📄 | 없음 ✅ |
| 착수까지 | 라이선스 확보 후 | **즉시** ✅ |
| 비용 | 정식 출시 후 미정 📄 | 0 ✅ |

**PoC가 진행될 수 있었던 유일한 이유다.** 라이선스를 기다렸다면 오늘 아무것도 없었다.

### 5.2 수신 이벤트 폭 (§3 역할1 참조)

SDK가 버리는 `delete`·`reaction`·봇알림을 전부 받는다 ✅.
완료 통보 기능은 이것 없이는 불가능했다.

### 5.3 프로토콜 결함 회피

SDK의 `sslopt` 누락과 사후 토큰 갱신을 우리 구현에서는 고쳤다 🔍✅.
정식 방식에서 SDK를 그대로 썼다면 **이 환경에서는 연결조차 되지 않았다.**

### 5.4 의존성

| 정식 | 자체 구현 |
|---|---|
| `dooray-sdk` + extras (langchain, cookiecutter 등) | `requests`, `websocket-client`, `certifi` |

폐쇄망 배포 시 부담 차이가 있다.

### 5.5 베타 의존 회피

SDK는 `0.1.0b1` 베타이고 deprecated 표면이 다음 마이너에서 제거 예정이다 🔍.
익스텐션 에이전트 자체도 *"정식 출시 전 기능, 스펙 변경 가능"*이다 📄.
자체 구현은 SDK 버전 업에 영향받지 않는다 — 다만 §6.1의 리스크로 되돌아온다.

## 6. 자체 구현 고유 리스크

### 6.1 프로토콜 변경 통보를 못 받는다

Dooray가 소켓 프로토콜이나 인증 방식을 바꾸면 **우리는 장애로 알게 된다.**
정식 사용자는 SDK 업데이트로 흡수되지만 우리는 아니다.

완화: SDK를 `.venv`에 남겨두고 새 릴리스가 나오면 소스 diff로 변경을 먼저 확인한다(`02` §12).

### 6.2 정식 경로가 아니다

Dooray가 개인 토큰의 socket-mode 접근을 의도적으로 제한하면 막힌다.
현재 막을 이유는 보이지 않으나(공용 엔드포인트, 본인 권한 범위 내),
**보장된 계약이 아니다.**

### 6.3 내부 승인

정식 기능 경로를 우회하는 구성이므로 운영 투입 전 내부 승인이 필요하다.
§4의 권한 문제가 보안 검토에서 반드시 제기될 것이다.

### 6.4 HA 구성

토큰당 활성 소켓 1개 제약(`1008`)은 **양쪽 동일**하다 ✅📄.
SDK는 중복 프로세스를 STANDBY로 두고 자동 승격시키지만 🔍,
자체 구현은 15초 재시도만 구현했다 — `replicas: 2` 무중단 전환은 직접 만들어야 한다.

## 7. 봇 전용 계정 — 제3의 선택지

§4의 문제 대부분은 **라이선스 없이도** 해소할 수 있다.
개인 계정이 아니라 **봇 전용 Dooray 계정**을 하나 만들어 그 계정의 개인 토큰을 쓰면 된다.

| 항목 | 개인 계정 (현행) | 봇 전용 계정 | 정식 에이전트 |
|---|---|---|---|
| 라이선스 | 불요 | 불요 | **필요** |
| 토큰 권한 격리 | ❌ | ✅ | ✅ |
| 발신자 표시 | 사람 이름 | 봇 이름 | 봇 이름 |
| 작성자 제약 회피 | ❌ | ✅ | ✅ |
| 감사 분리 | ❌ | ✅ | ✅ |
| 초대 기반 수신 제어 | ❌ (화이트리스트로 대체) | ❌ (동일) | ✅ |
| 킬 스위치 | 토큰 삭제 | 토큰 삭제 | 스튜디오 토글 |
| 조직도·프로필 | — | 일반 계정으로 표시 | 에이전트로 표시 |
| 비용 | 0 | **좌석 1** | 라이선스 |

**비용 대비 효과가 가장 큰 선택지다.**
좌석 1개로 §4의 4개 항목 중 3개가 해소된다.

남는 차이는 "초대 기반 수신 제어"와 "스튜디오 킬 스위치"인데,
전자는 화이트리스트로 대체하고 있고 후자는 토큰 삭제로 대응 가능하다.

## 8. 전환 판단 기준

### 지금 자체 구현으로 계속해도 되는 경우

- PoC·시연 단계
- 사용 범위가 담당자 본인과 소수 테스트 채널
- 처리하는 데이터가 마스킹 정책 확정 전이라 어차피 제한적

### 봇 전용 계정으로 옮겨야 하는 시점

- **실사용자가 담당자 본인을 넘어설 때**
- 발신자가 봇으로 보여야 할 때 (대외 시연 포함)
- 보안 검토를 받아야 할 때

### 정식 익스텐션 에이전트가 필요한 시점

- **초대 기반 수신 제어가 요구사항이 될 때**
  (누가 봇을 어디에 넣었는지를 Dooray가 관리해야 하는 경우)
- 스튜디오 킬 스위치가 운영 요건일 때
- Dooray AI를 LLM으로 쓰고 싶을 때 (`DoorayAIConfig`)
- Dooray의 공식 지원·프로토콜 변경 통보가 필요할 때

## 9. 기술미팅에서 확인할 것

이 비교에서 ❓로 남은 항목들이다.

1. **정식 에이전트에서 업무 상태 변경 알림이 오는가**
   작성자 제약이 풀리면 오는지, 아니면 상태 변경 알림 자체가 플랫폼에 없는지.
   → 폴링이 우회책인지 필수인지가 갈린다.
2. **에이전트 토큰의 실제 권한 범위**
   `services=[...]` 스코프가 어디까지 제한하는지. 문서에 없다.
3. **개인 토큰의 socket-mode 사용에 대한 Dooray 입장**
   막을 계획이 있는지. 있다면 정식 전환 일정을 앞당겨야 한다.
4. **AI 프리미엄 라이선스** — 테넌트 대상 여부, 할당 절차, 정식 출시 후 비용
5. **SDK 정식(GA) 릴리스 일정** — 현재 `0.1.0b1`

## 10. 결론

**Dooray가 정의한 익스텐션 에이전트의 역할 넷을 우리 구현은 모두 수행한다.**
기능적 차이는 크지 않고, 수신 이벤트 폭은 오히려 넓다.

차이는 **신원**에 있다. 봇이 독립된 주체인가, 사람의 계정을 빌려 쓰는가.
이 하나가 권한 격리·발신자 표시·감사 추적·작성자 제약을 전부 결정한다.

그런데 **그 차이의 대부분은 라이선스가 아니라 계정으로 해결된다**(§7).
봇 전용 Dooray 계정 하나면 좌석 1개 비용으로 실질적 문제가 대부분 사라진다.

→ **권고**: 봇 전용 계정 발급을 우선 추진하고,
   정식 익스텐션 에이전트는 §8의 조건이 발생할 때 전환한다.
