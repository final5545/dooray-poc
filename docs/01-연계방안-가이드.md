## 1. Extension Agent란

고객사 내부(DMZ 또는 내부망)에 위치하여 Dooray!와 고객사 시스템을 연결하는 **중개 서버**.

### 주요 역할

- Dooray! SDK(Python)를 통한 요청 수신
- 내/외부 DB 조회 (API, Search, RAG)
- 필요 시 외부 LLM 호출 및 응답 생성(추론)
- 보안 가이드라인을 준수하는 안전한 데이터 처리(프록시 역할)

### 활용 사례

**내부 레거시 연계**
- ERP·결재 연계 — "지난주 수요일 19:00~21:00 연장근로 수당 신청해줘"
- MES 연계 — "어젯밤 Line 2 생산 실적이랑 목표 대비 달성률 알려줘"

**외부 Web 연계**
- 뉴스 스크랩 봇 — 매일 아침 08:00 위키에 뉴스 스크랩 작성
- 공시 봇 — DART / EDGAR OpenAPI 활용 실적 보고서 작성
- 정해진 양식의 보고서 작성

## 2. 권한 모델

> Dooray 측 서술 (원문 취지 유지)

- 이 인터페이스는 **새로운 권한 체계를 만들지 않음**
- 고객사 내부 DB는 고객사가 자체 관리하는 인증·권한을 그대로 사용
- Dooray 쪽 응답은 사용자가 이미 가진 메신저 채널·AI 사이드앱 접근 권한 범위 내에서만 노출
- SDK는 발급된 `token` / `domain` / `services` 단위로 스코프가 고정 → Extension Agent가 임의로 다른 테넌트·서비스로 접근 범위를 넓힐 수 없음

**→ 부장님 질문 "Agent가 우리 DB에 어떻게 접근하는가"에 대한 답:**
Dooray는 우리 DB에 접근하지 않음. Extension Agent(우리가 만든 프로그램, 우리 서버에서 실행)가
평소처럼 직접 DB·사내 API에 붙음. 경계를 넘는 트래픽은 Dooray ↔ Agent 간 요청/응답뿐.

## 3. 연계 구성도 (요약)

```
<고객사 관리 영역>                          |    <Dooray! 관리 영역>
                                            |
 PaaS/sLLM        고객사 중개서버            |    Dooray!              LLM
 (OpenAI 등) <--> [Extension Agent #1]  <---+--> 메신저 챗봇(무료)   (Vertex AI:
              ③   [Extension Agent #2]  ①요청|    AI 사이드앱(유료)    Gemini/Claude)
                        |    ②             ④응답|    현재 페이지 요약
                        v                   |    화상회의 회의록      ※ Dooray! AI
                  [인사정보 DB]              |    마이 어시스턴트        서비스 이용 시
                  [연구관리 시스템]           |    프로젝트 PM
                                            |    DB(프로젝트/메일/캘린더/전자결재)
```

핵심:
- 시스템별로 **Extension Agent를 여러 개** 두는 구조 (#1, #2, ...)
- 점선(경계)을 넘는 것은 ①요청 / ④응답 뿐
- 외부 LLM 호출(③)은 고객사 영역 안에서 발생 → **토큰 비용 고객사 부담**
- 진입점: **메신저 챗봇(무료)** / **AI 사이드앱(유료)**

## 4. Case A — 고객사 DB 기반 답변 (Extension Agent)

**흐름**: Dooray 질의 → Extension Agent 중개(DB 검색 + LLM 추론) → Dooray 답변

| 단계 | 내용 |
|---|---|
| ① | Dooray! → Extension Agent: 사용자가 메신저 챗봇 또는 AI 사이드앱으로 질의 |
| ② | Extension Agent → 내부 DB: SDK 또는 API로 내부 DB 요청 (Search 또는 RAG) |
| ③ | 내부 DB → Extension Agent: 조회 결과 반환 |
| ④ | Extension Agent → 외부 LLM: 조회 결과를 컨텍스트로 구성해 추론 요청 (**토큰 비용 고객사 부담**) |
| ⑤ | 외부 LLM → Extension Agent: 생성 응답 수신 |
| ⑥ | Extension Agent → Dooray!: 최종 응답 전달 |
| ⑦ | Dooray! → 사용자: 응답 표시, 필요 시 메일·결재·위키 등 업무 기능 연계 |

### R&R

**고객사**
- Extension Agent 구축 (Dooray SDK 기반, Python)
- 내부 DB 연계 구현 (API / Search / RAG)
- 외부 LLM 사용 및 토큰 비용 부담 — DB 조회 → LLM 호출 → 결과 생성까지 고객사 책임

**Dooray**
- Dooray! AI를 통한 질의·응답 UI 제공
- 고객사 내부 DB 기반 답변을 Dooray 플랫폼으로 연결 (업무 등록, 메일 발송 등)
- AI Agent UI 별도 구현 불필요 — 메신저 AI 챗봇(무료) / AI 사이드앱(유료) 제공

### ⚠️ LLM 가드레일 — 고객사 책임 영역

이 경로는 Extension Agent가 **Dooray! AI 게이트웨이를 거치지 않고** 고객사 계약 외부 LLM에 직접 연결됨.
따라서 Dooray가 자사 LLM 연동에 제공하는 **지란지교 DLP·프롬프트 인젝션 탐지 등의 가드레일이 적용되지 않음.**

고객사가 직접 구성해야 하는 것:
- 프런티어 LLM(ChatGPT·Claude·Gemini) 호출 전후 민감정보 마스킹
- 프롬프트 인젝션 방어
- 요청·응답 로깅

금융보안원 「금융분야 AI 가이드라인」이 권고하는 **"인젝션 1차 차단 + 가드레일 2차 방어"** 다중 방어 구조가
필요한 경우, 고객사가 Extension Agent 또는 별도 게이트웨이 단에 직접 구성해야 함.

> 금융 데이터를 다루는 당사 특성상 이 항목은 설계 초기부터 반영 필요.

## 5. Case B — Dooray! 서비스 기반 답변 (Dooray! AI 일반 기능)

**흐름**: Dooray 질의 → 즉시 답변

- Dooray! AI가 Dooray 내부 DB(메일·전자결재·위키·드라이브)를 조회
- 조회 데이터를 컨텍스트로 연계 LLM(OpenAI, Gemini, Claude)에 추론 요청
- **LLM 비용은 Dooray! AI 구독 영역**

### R&R
- **고객사**: 없음
- **Dooray**: AI/UI 제공, Dooray DB 대상 Search·RAG, LLM 연계 및 비용을 구독 형태로 제공

> Case A와 Case B는 배타적이지 않음. 우리 DB 기반 기능은 Case A(구독 불필요),
> Dooray 자체 데이터 활용은 Case B(구독 필요)로 구분됨.

## 6. 가이드 원문의 SDK 설명 (⚠️ 현행 아님)

> 아래는 원문 보존용. **실제 코드 작성 시 사용 금지.**

### 설치 (원문)
```bash
unzip python-dooray-sdk.zip      # 또는 tar -xzf python-dooray-sdk.tar.gz
cd python-dooray-sdk
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt  # 또는 pip install -e .
```
→ **현행**: PyPI 공개. `pip install --pre dooray-sdk`

### Agent 클래스 (원문)
```python
class Agent:
    def __init__(self, token=None, domain=None, services=None, **kwargs)
```
→ 현행과 일치 (추가 파라미터 있음)

### 데코레이터 (원문)
```python
@agent.messenger   # 메신저 서비스 전체
@agent.task        # 업무 서비스 전체
@agent.wiki        # 위키 서비스 전체

def on(event_type="all", action=None, service=None)
```
→ `@agent.<service>` 형태는 현행에서 **deprecated** (DeprecationWarning 발생)

### 샘플 코드 (원문) — 사내 인사정보 휴가 조회
```python
import httpx
from dooray_sdk import Agent, query

agent = Agent(
    token="ext-agent-token",
    domain="customer.dooray.com",
    services=["messenger"],
)

@agent.messenger                       # ⚠️ deprecated
async def handle_message(event):
    user_question = event.text

    async with httpx.AsyncClient() as client:
        res = await client.get(
            "https://hr.internal.co.kr/api/vacation/balance",
            params={"employee_id": event.user_id},   # ⚠️ 존재하지 않는 속성
        )
        hr_data = res.json()

    prompt = f"""당신은 사내 HR 어시스턴트입니다.
사용자 질문: {user_question}
[인사정보 시스템 조회 결과]
- 이름: {hr_data['name']}
- 총 연차: {hr_data['total']}일
- 사용: {hr_data['used']}일
- 잔여: {hr_data['remaining']}일
..."""

    answer = ""
    async for message in query(prompt=prompt):
        answer += message.content

    await event.reply(answer)          # ⚠️ deprecated

agent.run()
```

**깨지는 지점**
| 원문 | 현행 |
|---|---|
| `@agent.messenger` | deprecated → `@agent.on("message")` |
| `event.user_id` | **존재하지 않음** → `req.actor.id` 또는 `req.data.senderId` |
| `event.reply(...)` | deprecated → `client.messenger.send_message(...)` |

### 샘플 코드 (원문) — 국세청 사업자등록 상태 조회

구조 동일. 2단계 LLM 사용 패턴이라 참고 가치 있음:
1. `query()`로 자연어에서 사업자등록번호(10자리) 추출 → 없으면 `"NONE"` 반환하도록 프롬프트 제약
2. 추출값 검증 (`if biz_no == "NONE" or len(biz_no) != 10`) 후 조기 반환
3. 국세청 API 호출 (`https://api.odcloud.kr/api/nts-businessman/v1/status`)
4. `query()`로 결과를 업무 맥락에 맞게 해석 (상태코드 01:계속사업자 / 02:휴업자 / 03:폐업자별 분기 안내)

> CRM 고객번호(E-code) 추출 시나리오에 그대로 응용 가능한 패턴.
> 단, 단순 코드 추출은 LLM 없이 정규식이 더 빠르고 저렴하고 정확함.
