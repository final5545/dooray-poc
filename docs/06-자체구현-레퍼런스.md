# 자체 구현 레퍼런스 — SDK 비의존 클라이언트

> 실측 기준일 2026-09-02. 도메인 `infomax.dooray.com`.
> **이 문서가 코드 작성 1순위.**
> SDK 소스에서 알아낸 것은 `02-sdk-분석에서-알아낸-것.md`,
> 진척·리스크는 `03-프로젝트-진척현황.md`.
>
> 검증 코드: `standalone/probe*.py` (실측 프로브 9종) / `standalone/agent.py` (실사용)

---

## 1. 배경 — 왜 SDK를 쓰지 않는가

익스텐션 에이전트는 **AI 프리미엄 라이선스** 보유자만 만들 수 있고,
`infomax.dooray.com`에는 AI 스튜디오 메뉴 자체가 없다.

SDK 소스 분석 결과 Socket Mode 인증이 에이전트 전용이 아니었고(`02` §2),
**설정 > API > 개인 액세스 토큰**(계정당 10개, 라이선스 무관)으로 연결에 성공했다.

SDK를 런타임에서 걷어낸 이유는 `02` §11. 요약하면 SDK가 필요한 프레임을 버리고,
이 환경에서 `sslopt` 누락으로 연결조차 안 되며, 토큰 갱신 방식이 1시간마다 단절을 만든다.

런타임 의존성은 `requests` + `websocket-client` + `certifi` 셋뿐이다.

## 2. 🔴 정식 에이전트와의 차이

| | 익스텐션 에이전트 | 개인 계정 소켓 (현행) |
|---|---|---|
| 라이선스 | AI 프리미엄 필요 | **불필요** |
| 정체성 | 봇 (별도 계정) | **사용자 본인** |
| 수신 범위 | **초대된** 대화방만 | 참여 중인 **모든** 대화방 |
| 초대 개념 | 있음 | **없음** |
| 발신·작성 표시 | 봇 이름 | **본인 이름** |
| 토큰 권한 | 봇 범위 | **본인과 동일** (메일·드라이브 포함) |
| 긴급 정지 | 스튜디오에서 '사용 안 함' | 토큰 삭제 |

**수신 범위가 정식 방식보다 넓다.** 초대라는 게이트가 없어 참여 중인 1:1·그룹방
메시지가 전부 유입된다. 실측에서 41명 그룹방, 8명 그룹방, 타인 1:1 DM 본문이 모두 들어왔다.

→ 화이트리스트가 선택이 아니라 **필수**다. 핸들러 첫 단계에서 허용 채널이 아니면
   본문을 남기지 않고 폐기해야 한다.

### 🔴 작성자 제약 — 설계를 가르는 지점

**Dooray는 업무 작성자에게 그 업무의 알림을 보내지 않는다.**
UI에서도 작성자는 참조자로 추가할 수 없다.

봇이 티켓을 만들면 봇이 항상 작성자다 → **봇은 자기 티켓의 알림을 영원히 못 받는다.**
완료 감지를 푸시로 못 하고 폴링으로 간 근본 원인이다(§10).

봇 전용 계정을 발급받아 작성자를 분리하면 해소된다.

## 3. 인증 체인

```
① POST https://api.dooray.com/common/v1/socket-mode/tokens
   Authorization: dooray-api {개인 액세스 토큰}
   Content-Type: application/json
   body: {}

   → result: { accessToken(JWT), tenantId, organizationMemberId }

② wss://infomax.dooray.com/messenger/v5/ws/{tenantId}/{organizationMemberId}
   Authorization: Bearer {accessToken}
```

API base URL은 도메인의 첫 서브도메인을 떼고 `api.`를 붙인다
(`infomax.dooray.com` → `api.dooray.com`).

### ⚠️ 소켓 토큰 수명 1시간

JWT 페이로드 `exp - iat = 3600`, `token_type: "web_socket"`.

SDK는 **끊긴 뒤에** 재발급한다(`02` §6.2) → 1시간마다 단절.
자체 구현은 만료 120초 전에 스스로 끊고 재발급해 무중단으로 처리한다.

### ⚠️ 토큰당 활성 연결 1개

중복 접속 시 close code **`1008 AGENT_ALREADY_CONNECTED`**.
개인 액세스 토큰에도 동일하게 적용된다(실측).

→ 개발 PC와 서버가 같은 토큰을 쓰면 한쪽이 **조용히** 밀린다.
   개인 토큰은 계정당 10개 발급 가능하므로 환경별로 분리할 것.

### ⚠️ macOS CA 스토어

`websocket-client`는 시스템 기본 CA 스토어를 쓰는데 macOS Python에서는 불완전해
`CERTIFICATE_VERIFY_FAILED`가 난다. `sslopt={"ca_certs": certifi.where()}` 필요.

`requests`(certifi 사용)는 통과하는데 WebSocket만 실패하므로 원인을 오해하기 쉽다.

## 4. WebSocket 프레임

### 프레임 종류 (실측 관측)

| `type` | `action` | 내용 |
|---|---|---|
| `sessionInfo` | `local` | 연결 수립. `content.sessionId` |
| `channelLog` | `create` | **메시지 수신** |
| `channelLog` | `update` | 메시지 수정, **봇 알림 본문 채움**(§5) |
| `channelLog` | `delete` | 메시지 삭제 |
| `channelMemberReadSeq` | `update` | 읽음 처리 (가장 빈번) |
| `reaction` | `update` | 이모지 반응 |
| `pong` | — | ping 응답 |

> `reaction`과 `channelLog delete`는 공식 문서에 없다.
> SDK는 `channelLog` + `create`/`update`만 통과시키므로 delete·reaction을 못 받는다.
> 이모지 반응은 버튼 UI 미지원(§9)의 대안 트리거로 쓸 수 있다.

**업무(task) 이벤트는 이 소켓으로 오지 않는다.** 티켓 생성·상태 변경 중 소켓을 열어두고
관측했으나 0건이었다. WS 경로가 `/messenger/v5/ws/`인 것과 일관된다.
SDK 레지스트리에 `task/task` 매핑이 있으나 향후 확장용으로 보인다(`02` §4).

### keepalive

`{"type":"ping"}` 를 주기적으로 send → `{"type":"pong"}` 수신.

### `content.type` — 메시지 종류 (실측)

| 값 | 의미 |
|---|---|
| `0` | 일반 메시지 |
| `1` | 시스템 메시지 (봇 초대/퇴장 등) |
| **`2`** | **봇 알림 (Dooray! News)** — §5 |
| `4` | 파일 첨부 |
| `10` | 답글(REPLY) |

### 일반 메시지 프레임

```json
{ "version": "5", "type": "channelLog", "action": "create",
  "content": {
    "id": "4412450644624024833",
    "channelId": "3267267775953625054",
    "senderId": "3267267451433100066",
    "text": "probe1",
    "type": 0,
    "sentAt": 1788309106490,
    "seq": 531,
    "directMemberId": "0",
    "token": "4feeb562-c700-41b1-8958-1ebe53bd5cd7",
    "flags": 0
  },
  "references": { "channelMap": { ... } },
  "channel": { "type": "me" } }
```

### 🔴 답글(`type: 10`)은 `text`가 이중 인코딩된다

```json
"text": "{\"type\":0,\"text\":\"답글 테스트\"}",
"originalLogId": "4412458658085482569"
```

`json.loads(text)["text"]`로 한 겹 벗겨야 본문이 나온다.
원본 메시지는 **`references.originalLogMap`**에 통째로 동봉되므로 별도 조회가 필요 없다.

> 답글(`type 10`)과 사이드바의 **글타래(스레드)**는 별개 기능이다.
> 공식 문서의 `parentChannelId`는 글타래 쪽으로 추정되며 미확인.

### 파일 첨부(`type: 4`)

```json
"text": "CLAUDE.md",
"file": { "id": "...", "fileName": "CLAUDE.md", "fileSize": 27023,
          "mimeType": "text/markdown", "forbiddenExtensionFlag": false }
```

> 🔴 공식 문서(`05` §5)의 "파일 첨부 필드 없음 → 수신 불가" 추정은 **틀렸다.**
> REST 응답에는 `drmEncryptType` 필드도 추가로 있다(금융권 파일 정책 검토 대상).

### `references.channelMap` — 채널 메타 전체 동봉

프레임마다 해당 채널의 메타데이터가 통째로 붙는다:
`type`, `scope`, `title`, `capacity`, `members[]`, `management.adminIds[]`, `preferences` …

→ 화이트리스트·권한 판정을 별도 API 호출 없이 처리할 수 있다.

### `channel.type` — 대화방 종류

| 값 | 의미 |
|---|---|
| `me` | 나와의 대화 (`capacity=1`) |
| `direct` | 1:1 대화 (`capacity=2`) |
| `private` | **주제 대화방** (제목 있음, `capacity=100`) |
| `bot` | **개인 봇 채널 = Dooray! News** (§5) |

## 5. Dooray! News — 업무 알림 채널

업무에 사람이 추가되면 Dooray-Bot이 알림을 보내는데, 그 도착지가 News다.

### 🔴 채널 ID가 자기 `memberId`와 같다

```
content.channelId == organizationMemberId
```

개인 봇 채널이라 **일반 대화방 목록(`/messenger/v1/channels`)에 나오지 않는다.**
채널 ID로 찾으려 하면 못 찾는다. 위 등식이 유일한 판별법이다.

### 프레임 구조 (실측)

```json
{
  "type": "channelLog", "action": "update",
  "content": {
    "channelId": "3267267451433100066",
    "type": 2,
    "senderId": "3262462486750041656",
    "customName": "Dooray-Bot",
    "customIconUrl": "https://dooray.com/static_images/icon/ic_stream_project.png",
    "text": "Task [@정시욱](dooray://3262462484277387103/members/3362258975191542304 \"member\")",
    "attachments": [{
      "color": "#6a7dd0",
      "title": "AI-PoC-Agent-Test/12: 알림 테스트",
      "titleLink": "https://infomax.dooray.com/project/tasks/4412603105543031023",
      "text": "TEST "
    }]
  }
}
```

| 필요한 정보 | 위치 |
|---|---|
| 업무 ID | `titleLink` 끝 — `/project/tasks/(\d+)` |
| 프로젝트 코드 / 번호 | `title` — `프로젝트코드/번호: 제목` |
| 업무 제목 | `title` 콜론 뒤 |
| 처리한 사람 | `text`의 멘션 — 이름과 memberId |
| News 판별 | `channelId == 내 memberId` + `customName == "Dooray-Bot"` |

### ⚠️ 함정 둘

**1. `action`이 `create`가 아니라 `update`인 프레임에 `attachments`가 채워진다.**
   먼저 오는 `create` 프레임에는 없다. `action == "create"`만 처리하면 놓친다.

**2. 참여 중인 전 프로젝트의 알림이 섞여 들어온다.**
   프로젝트 10여 개에 속해 있으면 남의 프로젝트 업무 알림도 온다.
   `title`의 프로젝트 코드로 거르지 않으면 권한 없는 프로젝트에 조회를 날려 403을 맞는다.

구현: `support/notify.py`

## 6. 🔴 Dooray 알림 규칙

하루를 들여 확인한 결과. **설계를 가장 크게 좌우한 부분이다.**

| 이벤트 | 알림 |
|---|---|
| 업무 **등록** | ✅ |
| 참조자·담당자 **추가** | ✅ |
| 상태 **변경**(완료 등) | ❌ |
| **자기 행동** | ❌ |
| **자기가 작성자인 업무** | ❌ |

### 확인한 푸시 경로와 결과

| 경로 | 결과 |
|---|---|
| WebSocket 업무 이벤트 | ❌ 0건 (메신저 전용 소켓) |
| 프로젝트 웹훅 REST | ❌ 404 (`/hooks`, `/webhooks` 전부 없음) |
| 일반 웹 훅 (UI) | 프로젝트명·멤버 변경용. 무관 |
| 업무 웹 훅 (UI) | "업무나 댓글이 **등록**될 때". **인바운드 오픈 필요** |
| 서비스 연동 (UI) | 외부 툴 → 업무 방향. 반대 |
| 자동화 (UI) | 조건에 "업무 상태를 변경" 있으나 **수행에 알림이 없음** |
| Dooray! News | 등록·사람추가에만 반응 |

### 자동화 규칙 (UI 전용, REST API 없음)

| 조건 | 수행 |
|---|---|
| 업무 상태를 변경 | 담당자 추가 |
| 새 업무를 등록 (+태그 필터) | 담당자 변경 |
| 업무 태그 추가 | 담당자 임의 변경 |
| 업무 만기일 변경 | 하위 업무 등록 (접두사·접미사·태그) |

**"완료 → 담당자 추가"가 동작하는 것은 실측 확인했다.**
다만 추가 대상이 봇(=작성자)이면 알림이 오지 않아 감지에 쓸 수 없다.

> 웹 훅은 Dooray가 **우리 서버로 인바운드 호출**하는 방식이다.
> Socket Mode를 택한 이유가 "공인 IP·인바운드 방화벽 불필요"였으므로(`00` §6),
> 사내망 배포 전제에서는 사실상 선택지가 아니다.

→ **완료 감지는 폴링으로 확정**(§10).

## 7. 🔴 루프 차단 — `token` 필드

소켓이 **본인 계정**에 붙으므로 본인이 친 명령도 `senderId == 본인`이다.
단순 자기필터를 걸면 **본인 명령까지 무시**되어 봇으로 쓸 수 없다.

구분 키는 `content.token`(UUID):

| 발신 경로 | `token` |
|---|---|
| 사람이 앱/웹에서 타이핑 | **있음** |
| REST API 발신 (우리 봇, 사내 알람봇 등) | **없음** |

```python
if sender == my_member_id and "token" not in content:
    return        # 우리가 보낸 응답 → 폐기
```

실측 검증: `#ping` 입력 → `pong` 1건만 발생, 재귀 없음.

> ⚠️ **`token`은 WebSocket 프레임 전용이다.** REST 조회 응답에는 이 필드가 없다.
> 메시지 백필·재처리 로직을 REST로 짜면 이 구분이 불가능하다.
>
> ⚠️ 부작용: **REST로 보낸 메시지는 우리 에이전트가 처리하지 않는다.**
> 테스트 시 사람이 직접 타이핑해야 한다.

## 8. REST API

인증 헤더는 동일하게 `Authorization: dooray-api {token}`.

### 메신저

| 목적 | 메서드 |
|---|---|
| 메시지 전송 | `POST /messenger/v1/channels/{channelId}/logs` body `{"text": "..."}` |
| 인용 답장 | `POST /messenger/v1/channels/{channelId}/logs/{messageId}/reply` |
| 메시지 조회 | `GET /messenger/v1/channels/{channelId}/logs?size=N` |
| 대화방 목록 | `GET /messenger/v1/channels` (News는 안 나옴) |
| 멤버 조회 | `GET /common/v1/members/{memberId}` |

전송 응답은 `result.id`(생성된 메시지 ID)를 돌려준다.
**실측 왕복 0.45초** — CRM 기획서의 3초 요건은 여유롭게 충족한다.

### 업무 (Project)

SDK가 미문서화로 감싸고 있는 영역인데 **REST는 정상 동작한다.**

| 목적 | 메서드 |
|---|---|
| 프로젝트 목록 | `GET /project/v1/projects?member=me` |
| 워크플로 정의 | `GET /project/v1/projects/{id}/workflows` |
| 업무 목록 | `GET /project/v1/projects/{id}/posts?size=100` |
| 업무 상세 | `GET /project/v1/projects/{id}/posts/{postId}` |
| 업무 생성 | `POST /project/v1/projects/{id}/posts` |
| 업무 수정 | `PUT /project/v1/projects/{id}/posts/{postId}` |
| 상태 전환 | `POST /project/v1/projects/{id}/posts/{postId}/set-workflow` |
| 프로젝트 생성 | `POST /project/v1/projects` |
| 위키 목록 | `GET /wiki/v1/wikis` |

**워크플로 `class`**: `registered` / `working` / `closed` 3종.
이름과 순서는 프로젝트별 커스텀이므로 **`class`로 찾아야 한다**(할 일/등록, 진행 중/진행 …).

**목록 응답에 `workflowClass`·`closed`·`updatedAt`이 이미 들어 있다.**
건별 상세 조회 없이 목록 1회로 전체 상태를 파악할 수 있다 — 폴링이 싼 이유(§10).

`postWorkflowClasses=closed` 필터도 동작한다.

**업무 수정(PUT)은 작성자를 바꾸지 않는다.** 남이 만든 업무의 본문만 고칠 수 있다.

**담당자·참조자 지정**
```json
"users": {
  "to": [{"type":"member","member":{"organizationMemberId":"..."}}],
  "cc": [{"type":"member","member":{"organizationMemberId":"..."}}]
}
```
담당자는 각자 개별 워크플로를 갖는다.
⚠️ **작성자를 참조자로 넣으면 무시된다**(§2). API는 200을 주지만 실제로는 비어 있거나 무효다.

### 없는 것

- 프로젝트 웹훅 (`/hooks`, `/webhooks`) — 404
- 자동화 규칙 (`/automations`, `/rules`) — 404. UI 전용
- Dooray! News 쓰기 (`/news/v1/*`) — 404

### 🔴 REST와 WebSocket의 스키마 차이

| 항목 | WebSocket | REST |
|---|---|---|
| 발신자 | `content.senderId` | `sender.member.organizationMemberId` |
| 메시지 종류 | 숫자 (`0`/`1`/`2`/`4`/`10`) | 문자열 (`NORMAL`/`REPLY`/`FILE`) |
| `sentAt` | epoch ms | ISO8601 |
| 답글 원본 | `originalLogId` (평면) | `originalLog.id` (중첩) |
| `token` | 있음 | **없음** |

두 경로를 섞어 쓰면 바로 깨진다. 변환 계층을 두는 편이 안전하다.

## 9. 메시지 표현 범위 (실측)

| 문법 | 지원 |
|---|---|
| 개행 (`\n`) | ✅ |
| `` `인라인 코드` `` | ✅ 빨간 글씨 + 회색 배경 |
| 표 (`\|---\|`) | ❌ 파이프 그대로 노출 |
| `**굵게**` | ❌ |
| `~~취소선~~` | ❌ |

**마크다운 지원은 인라인 코드 하나뿐이다.**

→ 카드는 **개행 + 유니코드 괘선 + 이모지**로 조립한다.
   사내 `통합모니터링_알림` 채널이 이미 쓰는 방식:

```
🚨 서버 리소스 위험

📍 서버: FS2
⚠️ CPU 99.7% (임계값 98.0%)
```

> 마스킹의 `*`는 마크다운 강조가 아니다(`010-****-5678`에는 강조할 내용이 없다).
> 게다가 굵게 자체가 렌더링되지 않으므로 현재는 무해하다.

## 10. 완료 감지 폴링

Dooray가 상태 변경 알림을 주지 않으므로(§6) 폴링한다.

```
목록 API 1회 호출 → {업무ID: workflowClass} → 직전 스냅샷과 비교
```

| 성질 | 내용 |
|---|---|
| 주기 | 300초 (`DOORAY_POLL_INTERVAL`) |
| 비용 | 호출 1회. 티켓이 몇 건이든 동일 |
| **누락** | **없음** — 스냅샷 비교라 프로세스가 죽었다 살아나도 이어진다 |
| 중복 | 없음 — 완료 전이만 1회 통보 |
| 첫 실행 | 통보 없이 스냅샷만 저장 |

### 설계 요점 셋

**주기는 지연만 결정한다.** "마지막 폴링 이후 변경분"을 묻는 게 아니라 저장된 스냅샷과
현재 상태를 비교하므로, 폴링이 몇 번 실패해도 다음 성공 때 한 번에 잡힌다.

**첫 실행은 통보하지 않는다.** 상태 파일이 없으면 스냅샷만 저장한다.
그러지 않으면 기존 완료 건 전부에 뒤늦은 알림이 나간다.

**처음 보는데 이미 완료면 무시한다.** 우리가 접수한 뒤 완료된 게 아니라
뒤늦게 시야에 들어온 건일 수 있다.

상태 파일은 `os.replace`로 원자적 교체 — 중간에 죽어도 깨지지 않는다.

### 원 요청 좌표

완료를 감지해도 "어느 대화방 어느 메시지에 답할지"를 알아야 한다.
Dooray 업무에는 그 정보를 담을 필드가 없으므로 **본문에 남긴다.**

```
[요청출처] channel=<채널ID> message=<메시지ID>
```

이 줄이 없는 업무(사람이 직접 만든 것 등)는 통보 대상에서 제외된다.

구현: `support/watcher.py`, `support/completion.py`, `support/ticket.py`

## 13. 보안 메모

- 개인 액세스 토큰은 **사용자 본인과 동일한 권한**이다. 메신저뿐 아니라
  메일·드라이브·프로젝트 전체에 접근 가능하므로 봇 전용으로 격리할 수 없다
- 자격증명은 `.env`(권한 600, `.gitignore` 등록)로 관리한다.
  환경변수를 명령줄에 직접 넣으면 `ps`로 노출된다
- 대화방 전체 유입이 기본값이므로 **로깅 정책**(원문 저장 여부·보존 기간)을
  코드보다 먼저 정해야 한다
- LLM 호출은 외부 전송이다. Dooray AI의 가드레일(DLP·인젝션 탐지)이 적용되지 않는다
- PoC 종료 후 Dooray 토큰·Anthropic 키 모두 폐기할 것

> **봇 전용 계정을 발급받으면** 토큰 권한 격리·발신자 표시·작성자 제약(§2)이
> 한 번에 해소된다. 우선순위 높은 후속 과제다.
