01자연어 요청 + 1회 확인액션 5 · 완료

지난 회의 — "현재의 해시·슬래시 명령과 다단계 양식은 사용성이 떨어지므로 자연어 요청과 1회 확인 중심으로 단순화"

지적대로 명령이 17종이었고, 양식 경로는 입력이 세 번 필요했습니다.

지난 회의 시점지금
요청하는 법#이전 → #기술정보 + 양식말하듯 쓴다
확인하는 법#확인"네"
입력 횟수3회2회
외울 명령17종없음 (양식은 선택)
  • "바꿔야"를 노후교체로, "다음주 화요일 오후"를 희망일시로 읽었습니다. 요청 유형 11종을 분류합니다.
  • 조회는 조회로 갑니다. "계약 언제 끝나지?" 같은 말에는 고객 카드가 나옵니다. 애매하면 조회 쪽으로 기웁니다.
  • 기존 명령(#이전 · #확인 · /접수)도 그대로 동작합니다. 익숙한 분은 계속 쓰실 수 있습니다.
업무를 자동으로 만들지는 않습니다. AI가 잘못 읽을 수 있고, Dooray에 업무 삭제 API가 없습니다. 잘못 만든 업무는 사람이 화면에서 지워야 하므로 확인 한 번이 그보다 쌉니다. 실제로 이 확인 단계 덕분에 개발 중 발견한 오류가 실제 업무로 이어지지 않았습니다.

02사내 CRM 실 API 연결액션 6 · 부분

지난 회의 — "CRM 개발서버와 실제 API가 연결되지 않아 실데이터 조회·양방향 상태동기화는 검증하지 못함"

고객정보 조회 API를 받아 연결했습니다. 응답 40ms로 실사용에 문제가 없습니다.

확인된 제약 — 필드 절반이 없습니다

기획서 §4가 요구한 항목 중 계약정보 전부와 설치정보 대부분, 이메일이 응답에 없습니다.

섹션기획서 요구실 API
기본정보고객번호 · 구분 · 고객명 · 기기전부 있음
사용자정보부서 · 이름 · 전화1 · 전화2 · 이메일전화2 · 이메일 없음
계약정보청구일 · 계약시작 · 종료 · 갱신전부 없음
설치정보설치일자 · 회선구분 · 통신사전부 없음
(신규)—주소 · 비고

값이 없는 게 아니라 응답에 항목 자체가 없어서, 빈 칸으로 늘어놓으면 "계약이 없는 고객"으로 오해됩니다. 지금은 해당 섹션을 통째로 생략해 보여줍니다.

확인이 필요합니다. 계약·설치정보를 화면에 넣으려면 API에 필드 추가가 필요합니다. 기술지원 담당자가 계약 종료일을 보고 판단하는 경우가 있다면 필요한 항목입니다.

망 접근

사무망(개발 PC)에서는 닿습니다. 서버망(ai-node)에서는 닿지 않습니다 — No route to host로, 포트가 아니라 경로가 없는 상태입니다. 현재는 조회·요청 기능이 개발 PC에서 돌고 있어 동작에 지장이 없지만, 운영 전환 시에는 방화벽 허용이 필요합니다.

03처리와 통보

요청이 등록된 뒤의 흐름입니다. 담당자는 대화방을 벗어나지 않습니다.

화면에 없는 것. Dooray 웹에서 직접 완료한 경우는 원 요청에 인용 답장이 달리며 최대 5분 걸립니다 — Dooray가 상태 변경에 알림을 주지 않아 주기적으로 확인합니다. 양식 경로(#이전 → #기술정보)는 자연어로 대체되어 뺐지만, 전화로 받아 적을 때는 여전히 유용합니다.

04보안 · 제어계층기본조건 5 중 3

지난 회의 — "승인 사용자·전용 채널 화이트리스트, 최소 필드 전송, 호출속도 제한, 감사로그와 별도 제어계층을 기본조건으로 검토"

실 CRM이 붙은 이상 "PoC라서"로 미룰 수 없다고 보아 오늘 두 가지를 더했습니다.

항목상태
전용 채널 화이트리스트있음 지정한 대화방 외에는 본문을 로그에도 남기지 않음
승인 사용자 화이트리스트있음 2026-09-10 추가. 명단에 없으면 안내만 돌려주고 아무것도 하지 않음
감사로그있음 2026-09-10 추가. 조회·생성·상태변경·거부를 별도 파일에 기록
최소 필드 전송스위치만 마스킹 기능은 있으나 기본 꺼짐 — 무엇을 가릴지 정책이 필요
호출속도 제한없음 CRM·LLM 호출에 제한 없음

승인되지 않은 사용자

CRM 조회 명단에 없는 계정으로 실제 시험
사용자
E120452 정보 좀 볼게
기술지원 도우미
이 기능은 승인된 담당자만 사용할 수 있습니다. 사용이 필요하시면 AI부에 말씀해 주세요.

고객번호를 알아도 조회되지 않습니다. 조회·요청·상태변경 모든 경로에 같은 확인이 걸립니다.

감사로그에 남는 것

{"at":"2026-09-10T14:02:34+0900","event":"lookup","user":"3267…066","channel":"4412…595","codes":["E120452"]}
{"at":"2026-09-10T14:47:59+0900","event":"denied","user":"3267…066","channel":"4412…595","route":"crm"}

위 두 줄은 같은 계정으로 승인 명단만 바꿔 시험한 실제 기록입니다 — 명단에 있을 때는 lookup, 없을 때는 denied로 남습니다.

무엇을 조회했는지만 남기고 결과는 남기지 않습니다. 고객번호와 시각·사용자는 기록하되 이름·연락처·주소는 기록하지 않습니다 — 로그 파일이 새로운 유출 경로가 되면 안 되기 때문입니다.

남은 둘은 정책 결정이 필요합니다. 최소 필드 전송은 무엇을 가릴지(연락처만? 주소도?), 호출속도 제한은 어느 선을 넘으면 이상으로 볼지를 정해야 만들 수 있습니다. 기능 자체는 어렵지 않습니다.

그 밖에

  • 양방향 상태 동기화 — Dooray 업무 상태 변경은 되지만 CRM 쪽과 맞추는 것은 미착수. 업무 API 스펙 확인 후
  • Dooray 라이선스·약관, 개인토큰 사용범위 — 확인되지 않음. 현재 개인 액세스 토큰으로 동작하며, 이는 토큰 소유자와 동일한 권한입니다

05결정을 청하는 사항

  1. CRM API 필드 추가 — 계약정보·설치정보를 화면에 넣을 것인지. 넣는다면 API에 필드 추가가 필요합니다.
  2. 업무관리 위치 — Dooray 프로젝트에 둘지, CRM으로 옮길지. 「Dooray는 요청 인터페이스, CRM은 원장」 방향에는 동의합니다. 다만 CRM 업무 API가 저희가 쓰는 여덟 가지 동작을 지원해야 성립합니다. 확인 항목을 별도 문서로 정리했습니다.
  3. 실사용 시작 시점과 보안 요건 — §4의 남은 둘(최소 필드 전송·호출속도 제한)을 선행 조건으로 볼지, 사용하면서 채울지.
  4. 서버망 → CRM 방화벽 — 운영 전환 시 필요합니다. 지금은 개발 PC에서 돌고 있어 급하지 않습니다.
다음 단계 제안. CRM 업무 API 스펙을 받는 것이 가장 앞섭니다 — 그것이 정해져야 원장 구조도, 상태 동기화도, 2차 시나리오도 설계할 수 있습니다. 그동안 저희는 남은 보안 항목의 정책안을 만들어 오겠습니다.
